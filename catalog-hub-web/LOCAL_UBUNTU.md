# Catalog Hub — локальная разработка на Ubuntu

Данное руководство относится к папке `catalog-hub-web` проекта [pro-cosmetics-shop-v2](https://github.com/itasik2/pro-cosmetics-shop-v2).

## Схема

- Интерфейс **Next.js** работает **локально** на `127.0.0.1:3001`: не нужен Vercel и не тратятся лимиты развёртываний.
- Backend пока остаётся в существующей **Supabase Edge Function** Catalog Hub.
- База товаров **облачная**, поэтому запись из локального приложения **по умолчанию отключена**.
- Для настоящей изолированной разработки создать отдельный Supabase-проект / ветку БД и скопировать туда тестовые товары без реальных секретов. Это отдельный шаг.
- ProCosmetics на продакшене и приложение Vercel при локальных изменениях не затрагиваются.

## 1. Подготовка Ubuntu

Требуются `git`, Node.js **22** и `npm`. Проверьте:

```bash
git --version
node --version
npm --version
```

Если Node.js старее 22, установите Node 22 LTS через nvm или другой надёжный менеджер версий.

## 2. Скачать проект

При первом запуске:

```bash
git clone https://github.com/itasik2/pro-cosmetics-shop-v2.git
cd pro-cosmetics-shop-v2
git fetch origin
git switch chore/catalog-hub-ubuntu-local-dev
cd catalog-hub-web
npm install
npm run local:init
```

Если папка проекта уже есть, вместо повторного клонирования выполните `git fetch origin` и `git switch chore/catalog-hub-ubuntu-local-dev` в корне репозитория. При наличии своих несохранённых изменений сначала сохраните их через Git или `git stash`, чтобы не потерять работу.

**Почему `npm install`?** В данном подпроекте нет актуального подтверждённого lock-файла; стандартный CI использует `npm install`. Позже можно добавить lock-файл и перейти на воспроизводимый `npm ci`.

`local:init` создаёт файл `.env.local` с правами **600**, случайным паролем для входа и секретом сессии. Файл не перезаписывается при повторном запуске.

## 3. Получить отдельный API-ключ

В локальном режиме **Vercel OIDC не действует** — нужен `CATALOG_HUB_API_KEY`.

Если у вас есть действующий ключ Catalog Hub, укажите его в **локальном** `.env.local`. В базе хранится **только SHA-256**, старый открытый ключ из базы восстановить нельзя.

При отсутствии ключа выполните:

```bash
npm run local:keygen
```

Скрипт **не изменяет Supabase**: он распечатает новый ключ, SQL для сохранения его хеша в таблице `public."CatalogApiKey"` и SQL для отзыва доступа. Вставьте SQL в **Supabase SQL Editor проекта Catalog Hub** (не Notify KZ), затем самостоятельно сохраните новый ключ в `CATALOG_HUB_API_KEY` файла `.env.local`.

**Важно:** API-ключ даёт широкие права к Catalog Hub API, даже когда интерфейс работает в режиме только чтения. Не отправляйте его в чат, не вставляйте в клиентский JavaScript и не публикуйте в Git.

## 4. Проверка соединения и запуск

```bash
npm run local:check
npm run local:dev
```

Откройте **http://127.0.0.1:3001** и войдите с паролем `CATALOG_HUB_UI_PASSWORD` из `.env.local`.

`local:check` проверяет конфигурацию, здоровье Supabase Edge и право **чтения** списка товаров. Ключ в лог не выводится. Если возникают ошибки `401` или `403`, проверьте добавление ключа, `CATALOG_HUB_API_URL` и авторизацию в Supabase.

## 5. Безопасная локальная разработка

```dotenv
CATALOG_HUB_LOCAL_MODE=true
CATALOG_HUB_LOCAL_WRITE_ENABLED=false
```

С этими значениями можно открывать каталог, категории, репрайсер, карточки, импортировать файл **для предварительного просмотра**. Любые POST/PUT/PATCH/DELETE, проходящие через `hubFetch`, блокируются до отправки в облачный API.

Кнопки сохранения карточек и складских операций в этом режиме **не запишут данные**. Из-за особенностей Next.js часть операций, например вход по паролю, остаётся локально доступной.

**Чтобы тестировать реальные изменения:** рекомендуется отдельный тестовый Supabase-проект с его отдельным ключом и URL. Только после этого включайте:

```dotenv
CATALOG_HUB_LOCAL_WRITE_ENABLED=true
```

Перезапустите `npm run local:dev` после изменения `.env.local`. Включение записи при подключении к рабочей базе ProCosmetics может изменить реальные цены, остатки и каталог.

## 6. Проверки, разработка, публикация

```bash
npm test
npm run typecheck
npm run build
```

Изменения файлов интерфейса видны в браузере автоматически после сохранения (Next.js Fast Refresh). Не нужно делать деплой Vercel после каждого изменения.

Обычный цикл: локальная ветка Git → `npm test` и `npm run build` → Pull Request в GitHub → проверки CI → **один** Production-деплой Vercel, когда есть готовый выпуск. При переходе на другую ветку проверяйте, содержит ли она локальные скрипты.

## Частые ошибки

| Симптом | Возможная причина |
|---|---|
| `catalog_hub_server_auth_not_configured` | Не указан API-ключ в `.env.local` |
| `401` от Supabase | API-ключ не существует, неактивен или неверен |
| `local_read_only_mode` | Сохранение отключено преднамеренно; работайте с тестовой средой |
| `EADDRINUSE` порт 3001 | На порту запущено другое приложение; остановите его |
| Login «Вход не настроен» | Не выполнен `npm run local:init` или пустой пароль |
| Долгий отклик | База пока в облаке; зависит от соединения и запросов |

## Границы текущего этапа

Это **локальная разработка интерфейса**, а не перенос производственной базы или Edge API на ноутбук. Продакшен на Vercel останется без изменений, пока не будет отдельно согласован и сделан релиз. Публикация через GitHub/Vercel не входит в локальные скрипты.


## 7. Поставщики и сохранённые настройки импорта

При локальном запуске откройте **http://127.0.0.1:3001/import**.

- Выберите файл поставщика XLSX/CSV/XML/JSON, нажмите **Проверить и показать изменения**.
- Проверьте автоматическое сопоставление колонок и при необходимости вручную установите SKU, штрихкод, цены и названия.
- Укажите имя поставщика и сохраните профиль. При следующей загрузке выберите профиль — сохранённые колонки подставятся автоматически.
- Ни исходные файлы, ни API-ключи в историю не записываются. Сохраняются только название профиля, соответствия колонок и метаданные предпросмотра.

Профили сохраняются в двух файлах на **вашем ноутбуке**:

```text
catalog-hub-web/.local-data/supplier-profiles.json
catalog-hub-web/.local-data/supplier-import-history.json
```

Эта папка добавлена в `.gitignore`. Данные **не сохраняются в Supabase и не публикуются в Vercel**; при переходе на другой компьютер или удалении папки локальные профили будут недоступны. Для резервного копирования следует сохранить `.local-data` отдельно в защищённом хранилище.

Профили локально можно сохранять даже при `CATALOG_HUB_LOCAL_WRITE_ENABLED=false`, поскольку это не изменение рабочих товаров. **Подтверждение применения изменений к товарам остаётся заблокированным** до подключения отдельной тестовой среды.

Автоматическая загрузка прайсов по расписанию и сетевые подключения к поставщикам **не включены** на этом этапе. Следующим шагом следует создать тестовое окружение для end-to-end проверки импорта и затем добавить планировщик с правилами обновления.


### Быстрая проверка без записи в Supabase

1. Запустите локальный сервер и откройте `http://127.0.0.1:3001/import`.
2. Выберите файл `catalog-hub-web/examples/supplier-preview-demo.csv`.
3. Нажмите **Проверить и показать изменения**. Ожидается два новых тестовых товара с пометкой «Новый товар».
4. Укажите имя поставщика «Demo», нажмите **Сохранить профиль с текущими колонками**.
5. Обновите страницу: профиль должен остаться в списке. В истории сохранится запись о предпросмотре.
6. Применение намеренно недоступно при `CATALOG_HUB_LOCAL_WRITE_ENABLED=false`. **Не включайте запись ради этого теста на рабочей Supabase.**


## 8. Изолированная тестовая база — без дополнительных платежей Supabase

**Эта секция относится к локальной ветке разработки, а не к Production.**

Чтобы безопасно тестировать применение импорта, изменение категорий,
складских остатков и репрайсинг, предусмотрен небольшой стек **Docker Compose**:
PostgreSQL 17 + локальный HTTP API (Deno), выполняющий тот же каталоговый
Edge-код, который используется в Supabase. Новый проект в Supabase не создаётся.

### Требования Ubuntu

Нужны Docker Engine, плагин `docker compose`, Node.js 22 и npm.
Проверьте запуск контейнеров и наличие доступных ресурсов:

```bash
docker --version
docker compose version
docker info
node --version
```

Если Docker не установлен или доступ запрещён, **не включайте запись**.
Сначала настройте Docker по официальному руководству для Ubuntu:
https://docs.docker.com/engine/install/ubuntu/

Локальные контейнеры занимают память ноутбука; при дефиците памяти
их можно остановить командой `npm run testdb:stop`.

### Запуск

Остановите Next.js сочетанием **Ctrl+C**, затем выполните в директории
`catalog-hub-web`:

```bash
npm run testdb:setup
```

Скрипт запускает контейнер PostgreSQL на **127.0.0.1:55432**, синхронизирует
структуру из версии `marketplace-hub/prisma/schema.prisma` **только с этой
локальной БД**, создаёт случайный локальный API-ключ и три вымышленных товара
`TEST-LOCAL-001…003`, запускает Deno API на **127.0.0.1:8000**.
Никакие живые данные ProCosmetics не копируются.

Важное: скрипт **не изменяет** текущий `.env.local`. Он сохраняет новую
конфигурацию в `.env.test.local` и ключ в
`catalog-hub-local/.test-credentials.json` с доступом только владельцу.

Чтобы переключиться на тестовую базу:

```bash
npm run testdb:use
npm run local:check
npm run local:dev
```

После переключения в UI появятся **3 искусственных товара**.
В форме импорта `/import` можно теперь создавать новые товары и черновики
согласования, поскольку локальные записи разрешены **только** для URL
`http://127.0.0.1:8000`. Изменение одного флага с рабочим URL Supabase
**не разрешит** запись: это дополнительно проверяет серверный код.

### Возврат к рабочей базе (режим только чтения)

Остановите Next.js и выполните:

```bash
npm run testdb:remote
npm run local:check
npm run local:dev
```

Первое переключение автоматически сохраняет прежнюю конфигурацию
`.env.local` в защищённую локальную копию `.env.remote.backup`.
Если прежнюю конфигурацию вручную изменили, скрипт не перезапишет её без
проверки.

### Остановка и сохранность данных

```bash
npm run testdb:stop
```

Остановка контейнеров **не удаляет** PostgreSQL-том. Для перезапуска
`npm run testdb:setup` сохраняет существующие тестовые товары и правки
(изначальные товары добавляются только при отсутствии).

**Не запускайте** `docker compose down -v` без намерения удалить всю
тестовую БД. Не пробрасывайте порты 55432/8000 наружу и не подключайте
к контейнерам настоящие токены маркетплейсов или рабочие секреты Supabase.

### Ограничения этой тестовой реализации

Это лёгкий PostgreSQL+Deno, не полный набор Supabase Auth/Storage/Realtime.
Здесь можно проверять Catalog Hub API и сценарии с товарами, но функции,
зависящие от других сервисов Supabase, требуют дополнительных интеграций.
Функциональность следует считать готовой к Production только после тестов
с полноценной моделью доступа и резервным копированием.

Для проверки тестовой БД нельзя использовать старые 112 реальных товаров:
они намеренно отсутствуют. При успешном `npm run local:check` ожидаются
**3** товара, а не 112. При проверке UI порты должны быть только localhost.


### Проверка полного цикла импорта в тестовой базе

После команд `npm run testdb:setup` и `npm run testdb:use`
оставьте веб-интерфейс запущенным через `npm run local:dev`. Во втором
терминале внутри `catalog-hub-web` выполните:

```bash
npm run testdb:import-e2e
```

Тест сначала **проверяет**, что активная конфигурация указывает
**только на `http://127.0.0.1:8000`** и что локальный ключ совпадает
с ключом из Docker. При любом несоответствии он завершится **без записи**.

Затем тест:
1. входит в локальный интерфейс по локальному паролю;
2. загружает случайный тестовый CSV с одним новым и одним существующим SKU;
3. убеждается, что получены статусы `CREATE` и `UPDATE`;
4. проверяет отказ сервера от подменённого подтверждения;
5. подтверждает создание нового товара и постановку существующего на проверку;
6. проверяет, что новый товар имеет **0** на складе, несмотря на
   количество в прайсе, а цена существующего не изменилась без согласования;
7. сверяет запись в локальном журнале импорта.

Команда **создаёт искусственный товар и черновик изменения** в
тестовой базе; повторные прогоны добавляют новые записи. Она не
подключается к рабочей Supabase и не выполняет операции на Kaspi.

Проверка импортёра также встроена в GitHub Actions и проходит там
в полностью изолированном Docker-окружении.
