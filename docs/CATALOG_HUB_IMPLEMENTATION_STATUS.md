Из каждого файла одна выбранная строка создана в изолированной БД с явно назначенными ценовыми колонками: собственный запас остался нулевым, повтор со старым fingerprint отклонён. Это не массовое применение или production E2E. Исходные даты старых прайсов не делают их пригодными для обновления текущих цен.

## Оставшиеся этапы

1. **P0:** расширенная сверка полного применения реальных прайсов и проверка фото по SKU/фасовке. Обратимое объединение вариантов и очередь на 10 000 строк реализованы и проверяются отдельно от боевых данных.
2. **P1:** PostgreSQL CI, дополнительные сценарии конкуренции, восстановление и reconcile; отдельный API резервов и эксплуатационные лимиты. Резервы заказов уже используют общий Inventory.
3. **P2:** полный контракт адаптеров/OpenAPI, worker доставки и мониторинг; отдельный репозиторий не создаётся без плана переноса.
4. **P3:** shadow diff реальных ProCosmetics Product/Variant/Order, подписанные события, выборочный cutover и проверенный rollback. Рабочий канал защищён от случайного включения.
5. **P4:** доступ владельца к одному магазину Kaspi, read-only инвентаризация полного набора офферов, сопоставления, подтверждённая загрузка и статусы. Подготовленный XML не доказывает, что Kaspi его принял.
6. **P5:** связать существующий безопасный репрайсер с канальными предложениями, финальная проверка маржи непосредственно перед публикацией, разрешённые источники конкурентов и выключатель.
7. **P6:** пользователи, роли, приглашения, регистрация второй организации, лимиты и SaaS-биллинг. Ключ API и OIDC не заменяют вход сотрудников.
8. **P7:** рабочие Ozon/Wildberries адаптеры после пилотов. Пока возвращается UNSUPPORTED, а не фиктивный успешный результат.

## Выпуск

Миграции по порядку: `20261103082032_catalog_core_orders_and_scoped_keys.sql`, `20261103115000_catalog_variants.sql`, `20261103122000_catalog_import_queue.sql` из `marketplace-hub/supabase/migrations/`.

Миграция добавляет таблицы и ревизию Inventory, CHECK/FK/RLS, привязку ключей и scopes. Цены и физические остатки не пересчитываются; валидация CHECK блокирует выпуск при неверном существующем балансе. Перед production нужен снимок/восстановление, проверка существующих остатков и привязка ключей; применимость допуска на production оценивается отдельно от технических решений по реализации.

Порядок и ограничения: [инструкция выпуска](CATALOG_HUB_CORE_RELEASE.md). После каждого завершённого пакета обновляется [handoff](CATALOG_HUB_HANDOFF_FOR_NEXT_CHAT.md).
