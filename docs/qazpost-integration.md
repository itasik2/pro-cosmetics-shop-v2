# Интеграция доставки: QazPost первым, CDEK вторым

## Решение

Для `procosmetics.kz` основной провайдер доставки — **QazPost**. Причины:

- в проекте уже есть серверный клиент Open Post API;
- уже работает прокси поиска адресов и новых почтовых индексов;
- в `Order` уже предусмотрены поля для внешнего отправления, трек-номера, тарифа, веса, ярлыка и provider data;
- официальный Open Post API заявляет сервисы индексов, расчёта стоимости, формирования адресного ярлыка и трекинга;
- QazPost имеет подходящие продуктовые коды для посылок по РК и почтоматов.

**CDEK** закладывается вторым адаптером, а не отдельной логикой в checkout. Это позволит подключить его без переписывания заказа, оплаты и уведомлений.

Новый общий контракт перевозчика расположен в:

`lib/shipping/provider.ts`

## Что уже реализовано

### Модель заказа

В `Order` уже есть:

- `shippingProvider`
- `shippingServiceCode`
- `shippingStatus`
- `shippingExternalId`
- `trackingNumber`
- `shippingPrice`
- `shippingWeightGrams`
- `shipmentLabelUrl`
- `shippingProviderData`
- `shippingUpdatedAt`
- `shippedAt`
- `deliveredAt`

Поэтому отдельную таблицу доставки на первом этапе создавать не требуется.

### Поиск адреса QazPost

Публичный endpoint магазина:

`GET /api/qazpost/address-search?q=...`

серверно обращается к официальному Open Post API:

`GET https://open.post.kz/npi-integration/api/npi/search?query=...`

Bearer token остается только на сервере.

Переменные Vercel:

```text
QAZPOST_API_TOKEN_PROCOSMETICS=<Bearer token QazPost>
QAZPOST_API_BASE_URL_PROCOSMETICS=https://open.post.kz
```

Официальная документация поиска индекса:

`https://open.post.kz/services/details/26`

Справочник продуктов и сервисов:

`https://open.post.kz/references`

## Подходящие услуги QazPost

По текущему официальному справочнику для интернет-магазина наиболее релевантны:

- `P103` — Посылка РК, товар до 20 кг, доставка по Казахстану;
- `P109` — Посылка на почтомат, товар до 20 кг;
- `P151` — Go Post Express посылка, до 30 кг;
- `P153` — Go Post City посылка, до 30 кг внутри города;
- `P154` — Go Post Standard посылка, до 75 кг по РК.

На MVP не следует показывать клиенту все тарифы подряд. Рекомендуемая политика:

1. стандартная доставка QazPost — основной вариант;
2. почтомат — если API подтверждает доступность для адреса/города;
3. Express — как дополнительный более дорогой вариант после получения точных договорных тарифов.

## Целевой клиентский сценарий

### Checkout

1. Покупатель начинает вводить адрес.
2. Сайт предлагает нормализованные адреса QazPost.
3. После выбора сохраняются полный адрес и новый почтовый индекс.
4. Сервер определяет вес заказа.
5. Сервер запрашивает доступные способы и стоимость доставки.
6. Покупателю показываются 1–3 понятных варианта доставки.
7. Выбранный `provider`, `serviceCode` и цена фиксируются в заказе сервером.
8. Итоговая сумма заказа пересчитывается только сервером.

Клиент никогда не должен присылать доверенную стоимость доставки самостоятельно.

## Этап 1. Нормализация адресов

Статус: **частично готово**.

Необходимо:

- сохранить выбранный `postcode`, а не только текст адреса;
- в checkout различать свободный текст и подтвержденный адрес QazPost;
- при недоступности API разрешать ручной адрес, но помечать его как непроверенный;
- не блокировать заказ из-за временного сбоя QazPost.

Рекомендуемые дополнительные поля заказа:

```text
shippingPostcode
shippingAddressVerifiedAt
shippingPickupPointCode
```

Их можно добавить отдельной миграцией при реализации расчёта тарифа.

## Этап 2. Вес и габариты

Сейчас `Order.shippingWeightGrams` уже существует, но вес товара в каталоге системно не хранится.

До автоматического тарифа нужно добавить в `Product`:

```text
weightGrams
packageLengthMm
packageWidthMm
packageHeightMm
```

Для товаров без заполненных данных применяем безопасный упаковочный профиль по умолчанию из серверной конфигурации. В админке товары без веса должны попадать в отдельный список, чтобы постепенно заполнить данные.

Нельзя рассчитывать тариф по косметическому объёму `50 ml = 50 g`: упаковка, стекло и коробка с удовольствием превращают такую арифметику в логистический анекдот.

## Этап 3. Расчёт доставки

В `lib/shipping/qazpost.ts` добавить адаптер `QazPostProvider`, реализующий общий контракт `ShippingProviderClient`.

Метод:

```text
quote(request) -> ShippingQuote[]
```

Он должен:

- принимать нормализованный адрес/индекс назначения;
- получать город/индекс отправителя из серверной конфигурации магазина;
- передавать фактический вес и габариты;
- использовать разрешенные договором QazPost product codes;
- нормализовать ответ API в общий `ShippingQuote`;
- иметь timeout;
- не раскрывать ответ провайдера клиенту целиком;
- кэшировать одинаковые расчёты на короткое время;
- при ошибке возвращать fallback-доставку либо просить администратора подтвердить стоимость, а не ломать checkout.

Точные endpoint и payload расчёта необходимо брать из **актуального B2B/Open Post контракта, выданного QazPost для учетной записи магазина**. В коде нельзя угадывать endpoint по старым примерам из интернета.

## Этап 4. Создание отправления

Автоматическое отправление создается только после допустимого бизнес-события:

- онлайн/переводная оплата подтверждена;
- либо заказ с оплатой при получении подтвержден администратором.

Метод:

```text
createShipment(request) -> CreatedShipment
```

Результат записывается в существующие поля:

```text
shippingExternalId
trackingNumber
shippingServiceCode
shippingPrice
shipmentLabelUrl
shippingProviderData
shippingStatus = CREATED
shippingUpdatedAt
```

Обязательна идемпотентность по `orderId`: повторный клик или retry не должен создавать две посылки.

Администратору вместо ручного ввода трек-номера показываем действия:

1. `Создать отправление`;
2. `Скачать/открыть ярлык`;
3. `Вызвать курьера`, если доступно по договору;
4. `Отменить отправление`, пока это разрешено провайдером.

Ручной режим оставляем как аварийный fallback.

## Этап 5. Трекинг без участия администратора

Добавить cron endpoint, например:

`/api/cron/shipping-sync`

Он выбирает заказы со статусами:

```text
CREATED
SHIPPED
IN_TRANSIT
```

и обновляет их через `provider.track()`.

Нормализованные статусы магазина:

```text
NOT_CREATED
CREATED
SHIPPED
IN_TRANSIT
DELIVERED
CANCELED
ERROR
```

При реальном изменении статуса:

- обновляется `shippingStatus`;
- обновляется `shippingProviderData`;
- устанавливается `deliveredAt` для доставки;
- покупателю отправляется Telegram/WhatsApp/email уведомление;
- администратор не участвует.

Частота для обычной доставки: раз в 1–3 часа достаточно. Нет смысла проверять посылку каждые две минуты: автомобиль Казпочты от этого быстрее не поедет.

## Этап 6. Почтоматы

После стандартной доставки подключить `P109`.

Нужны:

- API/справочник доступных почтоматов;
- выбор точки на checkout;
- хранение `shippingPickupPointCode`;
- проверка габаритов;
- отображение выбранного почтомата в заказе.

Почтомат стоит подключать вторым этапом, потому что он снижает нагрузку на курьерскую доставку и удобен для небольших заказов косметики.

## Этап 7. Второй провайдер CDEK

CDEK подключается через тот же `ShippingProviderClient`.

Официальная developer-платформа:

`https://developer.cdek.ru/`

Адаптер должен реализовать:

```text
quote()
createShipment()
cancelShipment()
track()
```

и дополнительно поддержать ПВЗ, если договор/методы API это позволяют.

Checkout не должен знать детали QazPost или CDEK. Он получает нормализованный массив `ShippingQuote[]` и отображает варианты.

Это позволит автоматически выбрать:

- самый дешёвый;
- самый быстрый;
- предпочитаемый магазином;
- доступный для конкретного города.

## Правило автоматического выбора

Для минимального участия администратора:

1. QazPost Standard — приоритет по умолчанию;
2. если QazPost API недоступен, использовать последний валидный тариф только в пределах короткого TTL либо показать фиксированный резервный тариф;
3. если подключен CDEK, сравнить доступные предложения;
4. не менять уже выбранный и оплаченный тариф после оформления;
5. спорные/ошибочные отправления выводить в очередь `Требует внимания`.

Администратор должен видеть только исключения, а не вручную оформлять каждую посылку.

## Безопасность интеграции

Для всех перевозчиков:

- API token/secret хранить только в Vercel Environment Variables;
- никогда не использовать `NEXT_PUBLIC_*` для секретов;
- запросы провайдера выполнять только с сервера;
- timeout 10–15 секунд;
- retry только для безопасных/идемпотентных операций;
- создание и отмену защищать idempotency key;
- не логировать полный телефон, адрес, токены и provider response с персональными данными;
- `shippingProviderData` сохранять в очищенном виде;
- административные действия защищать `requireAdmin()`;
- cron защищать `CRON_SECRET`;
- изменения статуса и создание отправления записывать в audit log.

## Что требуется от QazPost до включения автоматического создания

Нужно получить у QazPost для магазина:

1. B2B/Partners договор;
2. production Bearer token Open Post API;
3. перечень разрешенных product codes;
4. актуальную документацию методов расчёта тарифа;
5. актуальную документацию формирования/отмены адресного бланка;
6. метод получения ярлыка;
7. метод трекинга;
8. при необходимости API вызова курьера;
9. ограничения rate limit;
10. тестовую среду или тестовые реквизиты, если предоставляются.

После получения этих данных слой `lib/shipping/qazpost.ts` можно довести до автоматического создания отправлений без изменения остальной архитектуры магазина.

## Очередность внедрения

### P0

- получить production token QazPost;
- завершить сохранение индекса;
- добавить вес/габариты товара;
- реализовать `quote()`.

### P1

- `createShipment()`;
- ярлык;
- автоматическое сохранение трек-номера;
- cron трекинга;
- уведомления покупателя.

### P2

- почтоматы `P109`;
- вызов курьера;
- автоматическая обработка ошибок и retry.

### P3

- подключить CDEK как второй адаптер;
- автоматическое сравнение тарифа/срока;
- правила выбора перевозчика без участия администратора.
