# Catalog Hub: выпуск складского ядра и каналов

Этот пакет расширяет существующую Supabase, не создавая отдельный склад Marketplace Hub. Рабочие цены, остатки и заказы не переносятся автоматически.

## Предварительная проверка

1. Проверить PR: Web unit/typecheck/build, Marketplace Hub unit/typecheck/build, native Deno check и Docker/PostgreSQL core E2E.
2. Сделать доступный для восстановления снимок production БД; записать время, идентификатор и проверить восстановление в изолированном окружении. Исходный снимок не класть в Git.
3. Сохранить идентификатор текущего Vercel deployment и исходники Edge v20 для отката.
4. Проверить существующие балансы **чтением**:

```sql
SELECT count(*) AS invalid_balances
FROM public."Inventory" i
JOIN public."Product" p ON p."id"=i."productId"
JOIN public."Warehouse" w ON w."id"=i."warehouseId"
WHERE i."onHand"<0 OR i."reserved"<0 OR i."reserved">i."onHand"
   OR i."safetyStock"<0 OR p."organizationId"<>w."organizationId";
```

Ненулевой результат блокирует выпуск: требуется разбор каждой записи, а не тихая коррекция.

5. До второй организации привязать web deployment (`CATALOG_HUB_AUTH_ORGANIZATION_ID` в Edge, `CATALOG_HUB_ORGANIZATION_ID` в Web/AI) и каждый необходимый ключ к организации. Старый непривязанный ключ разрешён только при единственной организации. Явно привязанному ключу нужны scopes; `NULL` не даёт глобальных прав.
6. Секреты задавать средствами платформы. `secretRef` — имя серверной настройки, не значение токена. Содержимое ключей не выводить в CI или чат.

## Последовательность

1. Получить необходимый допуск на production в соответствии с ТЗ. Не считать успешный PR разрешением на боевые продажи.
2. Применить **одной транзакцией**, по порядку: `20261103082032_catalog_core_orders_and_scoped_keys.sql`, `20261103115000_catalog_variants.sql`, `20261103122000_catalog_import_queue.sql`, `20261106060351_catalog_reservations.sql`. Повторное применение допускается; в них нет пересчёта товарных цен или физических остатков.
3. Проверить CHECK/FK/RLS новых таблиц и отсутствие грантов `anon`/`authenticated`. Миграция сама валидирует ограничение баланса; некорректный старый остаток блокирует её выполнение вместо автоматического пересчёта.
4. Опубликовать весь каталог исходников `marketplace-hub/supabase/functions/catalog-hub/`, включая новые модули. Публикация только `runtime.ts` не является корректным деплоем.
5. Развернуть Web именно из проверенного коммита. Проверить `/health`: `apiVersion=1`, версия `0.12.0-edge`, возможности scoped-auth / stock-movements / order-events / channels / outbox / variants / durable-imports / reservations. `/ready` должен вернуть `schemaReady=true`: без таблиц, ревизии и валидированного ограничения сервер не заявляет готовность.
6. Авторизованный read-only smoke: каталог, категории, склады, журнал движений, список заказов, отдельные резервы, каналы. Не запускать `core-e2e.mjs` в production: он предназначен строго для loopback и вымышленных данных.
7. Сначала TEST + SHADOW. Затем проверить отдельный тестовый OWN_STORE канал. Код блокирует случайное включение ACTIVE для PRODUCTION и не отправляет XML в Kaspi.

## Проверяемые контракты

Все бизнес-маршруты определяют организацию из авторизации; `organizationId` в старых запросах разрешён только при совпадении. Новые записи требуют `Idempotency-Key`, кроме read-only preview. Повтор с другим содержимым возвращает `409`.

| Маршрут | Назначение | Scope |
| --- | --- | --- |
| `GET /v1/catalog/products/{id}/revisions` | История карточки, по 20 записей с курсором | `catalog:read` |
| `GET /v1/catalog/products/{id}/revisions/{revisionId}` | Значения до и после, причина блокировки отката | `catalog:read` |
| `POST /v1/catalog/products/{id}/revisions/{revisionId}/rollback` | Восстановление с `confirmed`, `reason`, `expectedVersion` и Idempotency-Key | `catalog:write`; для связи поставщика также `imports:write` |
| `GET /v1/inventory/balances` | Балансы, ревизии, курсор | `inventory:read` |
| `GET /v1/inventory/reconciliation` | Сверка заказов и отдельных резервов, до 100 пар товар/склад | `inventory:read` и `orders:read` |
| `GET/POST /v1/inventory/movements` | Журнал / подтверждённое движение | `inventory:read/write` |
| `GET/POST /v1/reservations` | Список / создание отдельного резерва | `inventory:read/write` |
| `GET /v1/reservations/{id}` | Состав и оставшееся количество | `inventory:read` |
| `POST /v1/reservations/{id}/release,ship,return` | Частичные освобождение, отгрузка и возврат | `inventory:write` |
| `GET /v1/orders` | Общие заказы, курсор | `orders:read` |
| `POST /v1/orders/events/preview` | Проверка резерва без записи | `orders:write` |
| `POST /v1/orders/events` | CREATED / CANCELED / SHIPPED / RETURNED | `orders:write` |
| `GET/POST /v1/channels` | Список / создание в SHADOW | `channels:read/write` |
| `/v1/channels/{id}/mode` | Смена режима с expectedVersion | `channels:write` |
| `/v1/channels/{id}/offers` | sellerSku, цена, буфер, предзаказ | `channels:read/write` |
| `/v1/channels/{id}/mappings` | Склады, категории, параметры полного фида | `channels:read/write` |
| `GET /v1/channels/{id}/feed-preview` | Проверенный Kaspi XML, checksum | `channels:read` |
| `GET /v1/channels/{id}/export` | OWN_STORE / ERP предложения, без закупочных цен | `channels:read` |
| `/v1/sync/outbox` | Статус очереди | `operations:read` |
| `/v1/sync/outbox/claim` | Аренда событий на 60 секунд | `operations:write` |
| `/v1/sync/outbox/{id}/ack,fail,retry` | Подтверждение, retry и dead letter | `operations:write` |

API не хранит реквизиты оплаты и персональные данные покупателей в CoreOrder. Внешний номер заказа отделён от идентификатора события.

Ответы Edge содержат `X-Request-Id`; прокси кабинета передаёт тот же идентификатор серверу. JSON ограничен при чтении потока, включая запросы без Content-Length.

Порядок блокировок: idempotency key → внешний заказ (для событий) → строка заказа/резерва → Product по отсортированным id → Inventory. Корректировки из существующего редактора тоже блокируют Product и пишут StockMovement/Outbox в той же транзакции.

Откат карточки проверяет версию Product и состояние SupplierProduct под блокировкой. Он записывает новую ProductRevision и событие `catalog.product_changed` в той же транзакции. Старые записи с одним снимком доступны в истории. Для новых снимков используется существующее JSON-поле ProductRevision.

Сохранение ручной правки и создание черновика поддерживают необязательный `sourceUrl` для аудита. При создании черновика `expectedUpdatedAt` блокирует устаревшее предложение. Обогащение предлагает фотографии после сопоставления идентичности и проверки файла, сохраняет источник и время проверки. Разрешение на использование фото подтверждает оператор при проверке предложения.

## Очередь

Событие попадает в outbox в одной транзакции с балансом/заказом. Worker получает leaseToken; без текущей аренды ack/fail запрещены. После ошибки — backoff с jitter, после восьми попыток — DEAD. Возврат DEAD в очередь требует явного подтверждения оператора. Зависшая восьмая аренда переводится в DEAD при следующем claim.

Внешняя доставка ещё не подключена: наличие outbox не означает синхронизацию с магазином. Нельзя подтверждать доставку до подтверждения получателя. После таймаута получатель должен дедуплицировать event ID/версию.

## Откат

- До подключения реального канала можно вернуть прежние frontend/Edge deployments и оставить добавленные таблицы для анализа. Автоматического DROP или удаления журнала нет.
- После реальных резервов нельзя просто вернуть старый складской процесс: сначала остановить приём событий и worker, сверить незавершённые резервы и очередь, затем выбрать компенсирующие движения либо исправленный forward deploy.
- Не обнулять `Inventory.reserved` SQL-запросом и не удалять CoreOrder/StockMovement. Возврат и отмена оформляются идемпотентными событиями.
- Добавление второй организации исключает откат к глобальной авторизации v20 без изоляционного шлюза. Это отдельный критерий допуска cutover.

## Известные границы

Это не полный P0–P7: остаются сотруднические роли/вход, внешняя доставка событий worker, shadow/cutover ProCosmetics, подтверждённый Kaspi-пилот и Ozon/WB. Сохранение канальной цены и подготовка выгрузки проверяют закупку, комиссию, расходы, целевую прибыль, маржу и минимальную/максимальную цену. Для торговой выгрузки обязательно финансовое правило; повышение границы после сохранения предложения блокирует новый XML. Автоматическое применение решений репрайсера, подтверждённые источники конкурентов и внешняя публикация остаются в P5.


## Варианты и очередь импорта

- `POST /v1/catalog/variants/preview,apply` (`catalog:write`) — явный выбор 2–50 SKU, общей карточки и названия. Apply требует подтверждения, fingerprint и Idempotency-Key. Общие поля отличаются — оператор видит конфликт и подтверждает источник. История исходных карточек сохраняется.
- `GET /v1/catalog/variants/{productId}` (`catalog:read`) — все индивидуальные варианты. В каталоге `cards=true` сворачивает их в одну карточку; SKU поиска находит общую карточку. Интеграционные списки сохраняют каждый SKU.
- `POST /v1/catalog/variants/groupings/{id}/undo` — откат только без последующих изменений карточек. Складские движения не откатываются вместе с группировкой. DB trigger блокирует скрытое изменение общих полей у члена группы, включая старые AI/import клиенты.
- `GET/POST /v1/imports`, `/{id}/rows`, `/{id}/seal`, `/{id}/process`, `/{id}/retry,cancel` используют `imports:read/write`. Загрузка chunks сама ничего не применяет; seal сверяет весь manifest. Каждая применяемая строка и её checkpoint фиксируются одной транзакцией. Повтор после сбоя не повторяет запись.
- До 10 000 строк, до 100 строк в HTTP chunk, до 10 незавершённых импортов организации, до трёх попыток ошибочной строки. Версия Product проверяется при применении. Снижения и спорные данные создают существующие change sets, физический запас никогда не берётся из прайса.
- Для постоянной обработки вне браузера: отдельный процесс `npm --prefix marketplace-hub run worker:imports`. Конфигурация: `CATALOG_IMPORT_WORKER_ENABLED=true`, `CATALOG_HUB_API_URL`, ограниченный ключ `CATALOG_HUB_API_KEY` с `imports:read` и `imports:write`, привязанный к одной организации. `--once` выполняет один цикл. HTTPS обязателен вне loopback. Процесс не отправляет данные в каналы.
- Worker не развернут автоматически. До его настройки кабинет продолжает подтверждённые задачи при открытой странице. UPLOADING не исполняется; прерванную подготовку можно продолжить тем же файлом и выбранным набором.
- `GET /v1/imports/{id}/rows` возвращает отчёт курсором; сырые payload не выдаются этим списком. Новые таблицы и read view закрыты для Supabase Data API ролей anon/authenticated.


## OWN_STORE: сравнение и подписанные события

Текущий контракт: [OpenAPI 3.1](../marketplace-hub/openapi/catalog-core-v1.json). Документ описывает новые маршруты ядра; старые AI/UI маршруты остаются совместимыми и не объявляются полным контрактом продукта.

`POST /v1/channels/{id}/shadow-preview` (`channels:read`) сравнивает загруженный снимок предложений `{sellerSku, price, available, title?}` с ядром. Возвращает отсутствующие SKU и изменения полей. `changesApplied=false`, `remoteVerified=false`: проверка файла не доказывает прямое подключение магазина. Кабинет умеет загружать такой JSON и скачивать предложения ядра. В канальный экспорт не попадают purchasePrice и служебный supplierImport; характеристики публикуются из явно выделенного `attributes.public` и фасовки варианта.

Для `POST /v1/channels/{id}/order-events` требуются одновременно API key и HMAC. Ключ можно ограничить scope `orders:write:{id}`; такой ключ не может вызывать общий orders endpoint или другой канал. `secretRef` подключения ссылается на отдельную серверную переменную `CATALOG_CHANNEL_SECRET_*`, секрет минимум 32 символа. Не использовать для подписи другие ключи инфраструктуры.

Подпись: `x-catalog-timestamp` — Unix seconds; `x-catalog-signature` — `v1=` + hex HMAC-SHA256 от `timestamp + "." + connectionId + "." + canonicalJson(originalBody)`. Canonical JSON рекурсивно сортирует ключи объектов, сохраняет порядок массивов и использует обычную JSON запись примитивов без дополнительных пробелов. Допустимое время ±300 секунд. Idempotency-Key и externalEventId защищают повторную доставку; свежая подпись не создаёт второй резерв.

Позиции внешнего события содержат sellerSku, externalWarehouseId и quantity; используются только сопоставленные SKU/склады. Отсутствующая, устаревшая или подменённая подпись отклоняется. HMAC не включает реальный магазин автоматически: сначала TEST, затем проверяемый pilot/cutover и отдельный допуск.

Создание и изменение карточек (Edge и Node), безопасное применение цены, склад и заказы записывают события в Outbox в той же транзакции. Внешний delivery worker остаётся отдельным подключением; import worker не подтверждает доставку в магазины.

## Сверка резервов

`GET /v1/inventory/reconciliation` сравнивает Inventory.reserved с суммой количества CoreOrderItem заказов RESERVED и оставшегося количества ReservationItem активных отдельных резервов. Каждая порция использует один SQL-снимок. Проверка включает пары из активных заказов даже при отсутствующей складской записи. Возвращаются MATCH, RESERVATION_SHORTFALL, UNASSIGNED_RESERVED или MISSING_BALANCE, текущая ревизия и время проверки. Необязательны productId, limit до 100 и cursor из nextCursor предыдущей порции.

Непривязанный резерв может относиться к прежней системе. Разбор проводится по документам и состоянию заказа. Отчёт доступен в разделе «Склад» и требует одновременно inventory:read и orders:read. С текущей версией отчёта требуется миграция отдельных резервов `20261106060351_catalog_reservations.sql`.


## Отдельные резервы

Новый API использует существующую Inventory вместе с заказами. Он не переносит и не переименовывает прежние резервы CoreOrder. Сверка возвращает orderReserved, standaloneReserved и их сумму expectedReserved; возвращённые и освобождённые единицы не входят в активный резерв.

Создание требует `confirmed=true`, reference до 128 символов, reason 5–500 символов и 1–100 позиций `{productId, warehouseId, quantity, expectedRevision}`. Количество 1–100000 на пару; повторы пары объединяются, ревизии должны совпадать. Reference уникален в организации: эквивалентный повтор с другим ключом возвращает текущий резерв, в том числе уже завершённый. Изменение состава или основания того же reference — 409. Ревизии склада проверяются при первом создании и не входят в бизнес-идентичность документа.

Каждое действие требует reason, confirmed, expectedVersion и Idempotency-Key. Необязательный items задаёт частичные количества, отсутствие items применяет всё доступное. Освобождение и отгрузка уменьшают `remaining=quantity-released-shipped`; возврат ограничен `returnable=shipped-returned`, пополняет onHand и не создаёт новый резерв. Допустим возврат частичной отгрузки, пока остаток документа ещё зарезервирован. Нулевые позиции в запрос не включаются.

Все позиции, StockMovement, Inventory, новая версия и outbox меняются одной транзакцией. Конфликт или нехватка одной позиции откатывает весь запрос. Повтор Idempotency-Key воспроизводит сохранённый ответ; новый ключ со старой версией отклоняется. Освобождение доступно на деактивированном складе; новые резервы, отгрузки и возвраты требуют активного склада. Автоматического истечения срока нет: незавершённый резерв хранится до явного действия оператора или интеграции.

В кабинете: «Склад» → операция «Резерв» → проверка → подтверждение. В разделе «Отдельные резервы» доступны частичные действия, основание, подтверждение и курсорная пагинация по 20 документов. Изменения обновляют список и сбрасывают прежнюю сверку. Заказы показываются в своём разделе и продолжают принимать идемпотентные события магазина.
