# Catalog Hub: выпуск складского ядра и каналов

Этот пакет расширяет существующую Supabase, не создавая отдельный склад Marketplace Hub. Рабочие цены, остатки и заказы не переносятся автоматически.

## Предварительная проверка

1. Проверить PR: Web unit/typecheck/build, Marketplace Hub unit/typecheck/build, native Deno check и Docker/PostgreSQL core E2E.
2. Сделать доступный для восстановления снимок production БД; записать время, идентификатор и проверить восстановление в изолированном окружении. Исходный снимок не класть в Git.
3. Сохранить идентификатор текущего Vercel deployment и исходники Edge v20 для отката.
4. Проверить существующие балансы **чтением**:

```sql
SELECT count(*) AS invalid_balances
FROM public."Inventory" i
JOIN public."Product" p ON p."id"=i."productId"
JOIN public."Warehouse" w ON w."id"=i."warehouseId"
WHERE i."onHand"<0 OR i."reserved"<0 OR i."reserved">i."onHand"
   OR i."safetyStock"<0 OR p."organizationId"<>w."organizationId";
```

Ненулевой результат блокирует выпуск: требуется разбор каждой записи, а не тихая коррекция.

5. До второй организации привязать web deployment (`CATALOG_HUB_AUTH_ORGANIZATION_ID` в Edge, `CATALOG_HUB_ORGANIZATION_ID` в Web/AI) и каждый необходимый ключ к организации. Старый непривязанный ключ разрешён только при единственной организации. Явно привязанному ключу нужны scopes; `NULL` не даёт глобальных прав.
6. Секреты задавать средствами платформы. `secretRef` — имя серверной настройки, не значение токена. Содержимое ключей не выводить в CI или чат.

## Последовательность

1. Получить необходимый допуск на production в соответствии с ТЗ. Не считать успешный PR разрешением на боевые продажи.
2. Применить **одной транзакцией** миграцию `20261103082032_catalog_core_orders_and_scoped_keys.sql`. Повторное применение допускается; в ней нет пересчёта товарных цен или физических остатков.
3. Проверить CHECK/FK/RLS новых таблиц и отсутствие грантов `anon`/`authenticated`. Миграция сама валидирует ограничение баланса; некорректный старый остаток блокирует её выполнение вместо автоматического пересчёта.
4. Опубликовать весь каталог исходников `marketplace-hub/supabase/functions/catalog-hub/`, включая новые модули. Публикация только `runtime.ts` не является корректным деплоем.
5. Развернуть Web именно из проверенного коммита. Проверить `/health`: `apiVersion=1`, версия `0.10.0-edge`, возможности scoped-auth / stock-movements / order-events / channels / outbox. `/ready` должен вернуть `schemaReady=true`: без таблиц, ревизии и валидированного ограничения сервер не заявляет готовность.
6. Авторизованный read-only smoke: каталог, категории, склады, журнал движений, список заказов, каналы. Не запускать `core-e2e.mjs` в production: он предназначен строго для loopback и вымышленных данных.
7. Сначала TEST + SHADOW. Затем проверить отдельный тестовый OWN_STORE канал. Код блокирует случайное включение ACTIVE для PRODUCTION и не отправляет XML в Kaspi.

## Проверяемые контракты

Все бизнес-маршруты определяют организацию из авторизации; `organizationId` в старых запросах разрешён только при совпадении. Новые записи требуют `Idempotency-Key`, кроме read-only preview. Повтор с другим содержимым возвращает `409`.

| Маршрут | Назначение | Scope |
| --- | --- | --- |
| `GET /v1/inventory/balances` | Балансы, ревизии, курсор | `inventory:read` |
| `GET/POST /v1/inventory/movements` | Журнал / подтверждённое движение | `inventory:read/write` |
| `GET /v1/orders` | Общие заказы, курсор | `orders:read` |
| `POST /v1/orders/events/preview` | Проверка резерва без записи | `orders:write` |
| `POST /v1/orders/events` | CREATED / CANCELED / SHIPPED / RETURNED | `orders:write` |
| `GET/POST /v1/channels` | Список / создание в SHADOW | `channels:read/write` |
| `/v1/channels/{id}/mode` | Смена режима с expectedVersion | `channels:write` |
| `/v1/channels/{id}/offers` | sellerSku, цена, буфер, предзаказ | `channels:read/write` |
| `/v1/channels/{id}/mappings` | Склады, категории, параметры полного фида | `channels:read/write` |
| `GET /v1/channels/{id}/feed-preview` | Проверенный Kaspi XML, checksum | `channels:read` |
| `GET /v1/channels/{id}/export` | OWN_STORE / ERP предложения, без закупочных цен | `channels:read` |
| `/v1/sync/outbox` | Статус очереди | `operations:read` |
| `/v1/sync/outbox/claim` | Аренда событий на 60 секунд | `operations:write` |
| `/v1/sync/outbox/{id}/ack,fail,retry` | Подтверждение, retry и dead letter | `operations:write` |

API не хранит реквизиты оплаты и персональные данные покупателей в CoreOrder. Внешний номер заказа отделён от идентификатора события.

Ответы Edge содержат `X-Request-Id`; прокси кабинета передаёт тот же идентификатор серверу. JSON ограничен при чтении потока, включая запросы без Content-Length.

Порядок блокировок: idempotency key → внешний заказ (для событий) → строка заказа → Product по отсортированным id → Inventory. Корректировки из существующего редактора тоже блокируют Product и пишут StockMovement/Outbox в той же транзакции.

## Очередь

Событие попадает в outbox в одной транзакции с балансом/заказом. Worker получает leaseToken; без текущей аренды ack/fail запрещены. После ошибки — backoff с jitter, после восьми попыток — DEAD. Возврат DEAD в очередь требует явного подтверждения оператора. Зависшая восьмая аренда переводится в DEAD при следующем claim.

Внешняя доставка ещё не подключена: наличие outbox не означает синхронизацию с магазином. Нельзя подтверждать доставку до подтверждения получателя. После таймаута получатель должен дедуплицировать event ID/версию.

## Откат

- До подключения реального канала можно вернуть прежние frontend/Edge deployments и оставить добавленные таблицы для анализа. Автоматического DROP или удаления журнала нет.
- После реальных резервов нельзя просто вернуть старый складской процесс: сначала остановить приём событий и worker, сверить незавершённые резервы и очередь, затем выбрать компенсирующие движения либо исправленный forward deploy.
- Не обнулять `Inventory.reserved` SQL-запросом и не удалять CoreOrder/StockMovement. Возврат и отмена оформляются идемпотентными событиями.
- Добавление второй организации исключает откат к глобальной авторизации v20 без изоляционного шлюза. Это отдельный критерий допуска cutover.

## Известные границы

Это не полный P0–P7: остаются единственная общая карточка вариантов, асинхронный импорт, сотруднические роли/вход, реальный worker, shadow/cutover ProCosmetics, подтверждённый Kaspi-пилот и Ozon/WB. Сохранение канальной цены и подготовка выгрузки проверяют закупку, комиссию, расходы, целевую прибыль, маржу и минимальную/максимальную цену. Для торговой выгрузки обязательно финансовое правило; повышение границы после сохранения предложения блокирует новый XML. Автоматическое применение решений репрайсера, подтверждённые источники конкурентов и внешняя публикация остаются в P5.
