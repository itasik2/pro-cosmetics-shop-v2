# Доставка уведомлений Catalog Hub v1

Пакет P2: один получатель OWN_STORE на ChannelConnection, до десяти получателей организации. Это доставка уведомления об изменении с подтверждением записи во входящую очередь. Публикация предложений и применение снимка конкретным магазином — отдельный этап P3.

## Поток

1. Изменение товара, склада или предложения и OutboxEvent сохраняются одной транзакцией.
2. SQL trigger создаёт OutboxDelivery для каждого подходящего получателя. Отказ или rollback источника откатывает доставки. Edge и Node используют одинаковый механизм.
3. Worker берёт одну доставку в аренду на 60 секунд, отправляет подписанный immutable envelope и проверяет подписанное подтверждение.
4. Получатель сначала сохраняет уникальную запись inbox, затем подписывает ACK. Ядро повторно проверяет ACK перед DELIVERED.
5. Обработчик магазина читает разрешённый экспорт своего подключения и применяет его с проверкой версий/финансовых правил. Получение уведомления не доказывает публикацию.

Регистрация сериализуется с транзакциями источника общей/исключительной advisory-блокировкой. Если прежняя транзакция ещё не завершена, настройка получателя и её начальный refresh дожидаются commit. Изменения после регистрации видят уже сохранённого получателя.

OutboxEvent остаётся общим журналом источника. OutboxDelivery хранит отдельный результат каждого получателя: успешный приём одним магазином не завершает работу остальных. Для внешних доставок действует свой предел 100 текущих аренд; внутренняя outbox-очередь сохраняет свой предел 100.

## Какие изменения передаются

- catalog.product_changed — только для активного ChannelOffer этого товара или его общей карточки.
- inventory.changed — для SKU с активным предложением подключения. Уведомление не содержит склада или количеств; экспорт возвращает только сопоставленные склады. Такая инвалидация не пропустит изменение на границе нового сопоставления.
- channel.offer_changed / channel.mappings_changed — только адресованному подключению.
- catalog.variants_grouped / catalog.variants_ungrouped — если подключению принадлежит один из затронутых вариантов.
- channel.refresh_requested — обязательное обновление после создания или изменения адреса/секрета/topics получателя.

В payload передаются version=1, deliveryId, eventId, organizationId, connectionId, generation, type, time и data={refresh:"channel-export"}. Закупка, цены, исходный payload события, actor, поставщик, описания, реквизиты заказа и чужие SKU не передаются. DB CHECK ограничивает поля envelope и содержимое data. При получении магазин запрашивает актуальный экспорт; уведомления не несут складских дельт, которые могли бы примениться повторно или не по порядку.

## Настройка

GET/POST /v1/channels/{id}/webhook использует channels:read/write. В кабинете — «Каналы продаж» → собственный магазин → «Доставка событий». Новая настройка сохраняется приостановленной, без сетевого обращения. Для изменения требуются reason 5–500 символов, confirmed=true, expectedVersion и Idempotency-Key.

```json
{
  "url": "https://store.example/api/catalog-events",
  "secretRef": "CATALOG_DELIVERY_SECRET_MY_STORE",
  "topics": ["catalog.product_changed", "inventory.changed", "channel.offer_changed"],
  "state": "PAUSED",
  "expectedVersion": 0,
  "confirmed": true,
  "reason": "Подключение проверенного тестового получателя"
}
```

Значение секрета не вводится в браузер. Настройка secretRef ссылается на серверную переменную CATALOG_DELIVERY_SECRET_*: одинаковое случайное значение минимум 32 символа задаётся в Edge, worker и получателе. Для входящих событий заказа используется отдельный CATALOG_CHANNEL_SECRET_*, эти контракты не смешиваются.

Включение ACTIVE требует активного OWN_STORE в среде TEST и настроенного секрета Edge. Рабочий PRODUCTION остаётся заблокирован до пилота и cutover. Новый URL должен использовать HTTPS/443, без логина, пароля, query и fragment. Worker разрешает только точные хосты из CATALOG_DELIVERY_ALLOWED_HOSTS, проверяет все DNS-ответы, отклоняет частные/служебные адреса, закрепляет соединение за проверенным IP и не следует перенаправлениям. Ответ ограничен 8192 байтами, внешнее обращение — 10 секундами.

Только для изолированных loopback-тестов одновременно в Edge и worker включается CATALOG_DELIVERY_ALLOW_LOOPBACK_TEST=true; тогда разрешён HTTP 127.0.0.1. Рабочие окружения оставляют эту настройку выключенной.

Изменение URL, secretRef или topics повышает generation, отменяет незавершённые задания прежней конфигурации и создаёт новый refresh. Пауза/возобновление меняют version, сохраняют generation и накопленную очередь. Уже отправленный сетевой запрос отозвать нельзя; история прежнего адреса и подтверждений сохраняется.

## Запуск worker

Команда: `npm --prefix marketplace-hub run worker:deliveries`. Нужны:

| Переменная | Значение |
| --- | --- |
| CATALOG_DELIVERY_WORKER_ENABLED | true, явное включение |
| CATALOG_HUB_API_URL | HTTPS адрес ядра, либо изолированный loopback API |
| CATALOG_HUB_API_KEY | ключ одной организации с operations:read и operations:write |
| CATALOG_DELIVERY_ALLOWED_HOSTS | точные хосты получателей через запятую, без wildcard |
| CATALOG_DELIVERY_SECRET_* | серверные секреты по зарегистрированным именам |
| CATALOG_DELIVERY_MAX_PER_CYCLE | 1–10, по умолчанию 5 |

--once выполняет один цикл и возвращает ненулевой exit при ошибке или неопределённом подтверждении. SIGTERM/SIGINT прекращает новые запросы. При сбоях применяется backoff с jitter до 60 секунд. Получательский Retry-After учитывается до 3600 секунд. Нельзя записывать полный ответ получателя, URL или ключи в логи; сохраняются только безопасный код, deliveryId и счётчики.

Официальный worker арендует по одному заданию, чтобы очередь ожидания внутри процесса не расходовала срок следующих аренд. Повторы HTTP к ядру используют прежний Idempotency-Key. Если получатель уже подтвердил запись, а ответ complete ядра потерян, worker оставляет аренду для восстановления, не делает слепой fail. После истечения новый процесс повторяет тот же envelope; получатель отвечает DUPLICATE с новым временем и подписью.

## Подпись

JSON canonical: рекурсивно отсортировать ключи объектов, сохранить порядок массивов, записать обычным JSON без пробелов. Для текущего envelope все ключи фиксированы. SHA-256 canonical JSON — payloadHash.

Запрос содержит x-catalog-delivery-timestamp (Unix seconds) и x-catalog-delivery-signature (v1= + hex HMAC-SHA256). Подписываемая строка:

```text
catalog-delivery-v1\nTIMESTAMP\nCANONICAL_ENVELOPE
```

Здесь \n — один настоящий перенос строки. Допустимое отклонение часов ±300 секунд. ACK подписывается отдельным доменом:

```text
catalog-delivery-ack-v1\nTIMESTAMP\nCANONICAL_ACK
```

Ответ HTTP 200 application/json содержит ровно deliveryId, eventId, connectionId, payloadHash, status=ACCEPTED|DUPLICATE. Заголовки ответа: x-catalog-ack-timestamp и x-catalog-ack-signature. Сам по себе HTTP 200, пустой ответ, подменённый connectionId, неверный хеш или подпись не завершают доставку.

Ядро принимает POST /v1/sync/deliveries/{id}/complete только с текущим leaseToken, действующей generation и корректным ACK. Подтверждение хранится вместе с временем приёма. Изменять эти значения через обычный кабинет нельзя.

## Код получателя

Node SDK: marketplace-hub/src/worker/delivery-receiver.ts и delivery-contract.ts. createDeliveryReceiver принимает фиксированные organizationId, connectionId и secret серверной конфигурации; контекст не выбирается из тела запроса. Callback persist обязан завершить транзакцию до ACCEPTED. Готовый postgresDeliveryInbox использует уникальность (organizationId, connectionId, deliveryId) и сравнивает hash при повторе.

DDL marketplace-hub/integrations/catalog-delivery-inbox.sql устанавливается в базе получающего приложения отдельной миграцией. Он не входит в миграции Catalog Core. Таблица закрыта от публичного доступа; backend получателя использует выделенную серверную роль с нужными правами. В тесте получатель размещён в изолированной базе, реальный магазин не меняется.

Пример в серверном Node-приложении, где SQL-клиент и модули SDK уже подключены:

```ts
const handle = createDeliveryReceiver({
  organizationId: configuredOrganizationId,
  connectionId: configuredConnectionId,
  secret: configuredDeliverySecret,
  persist: postgresDeliveryInbox(receiverDatabase),
});
```

Приложение передаёт свой HTTP Request в handle и возвращает Response без изменения подписи. Inbox подтверждает запись уведомления. Для чтения Core получателю достаточно отдельного ключа channels:read:{id}. Экспорт сохраняет проверки финансовой политики. Ключ отправляющего worker остаётся в Core.

### Теневой снимок получателя

В базе получателя после catalog-delivery-inbox.sql установите marketplace-hub/integrations/catalog-store-shadow.sql. Снимок хранится в CatalogStoreShadowSnapshot по организации и подключению. Серверная роль получателя должна иметь доступ к своим строкам inbox и снимка. Для входящего webhook используется прежний подписанный SDK.

Потребитель запускается командой `npm --prefix marketplace-hub run worker:store-snapshot`. Настройки задаются на сервере получателя.

| Переменная | Значение |
| --- | --- |
| CATALOG_STORE_SNAPSHOT_ENABLED | true |
| CATALOG_STORE_DATABASE_URL | адрес базы получателя |
| CATALOG_HUB_API_URL | HTTPS адрес Catalog Core |
| CATALOG_STORE_EXPORT_KEY | ключ только с channels:read:{id} |
| CATALOG_STORE_ORGANIZATION_ID | организация получателя |
| CATALOG_STORE_CONNECTION_ID | подключение получателя |

`--once` выполняет один цикл. Для изолированного HTTP API на 127.0.0.1 включите CATALOG_STORE_ALLOW_LOOPBACK_TEST. Потребитель читает до 500 ожидающих уведомлений и запрашивает полный экспорт выбранных предложений. Он проверяет подключение, версию, уникальность SKU и складов, цены и количества. Ответ ограничен 16 МиБ и 10 000 предложений.

Запись снимка и отметка обработанных уведомлений выполняются одной транзакцией. Для подключения одновременно работает один потребитель. Уведомления, поступившие во время запроса экспорта, остаются на следующий цикл. При недоступности API или некорректном экспорте прежний снимок доступен для сверки, а уведомления остаются PENDING. Ревизия меняется только при изменении данных. Снимок используют для теневой проверки. Для подключения к продаже требуется проверенное переключение витрины и заказов.

## Диагностика и выпуск

GET /v1/sync/deliveries: операции одной организации, status, webhookId, cursor, limit до 100. Кабинет показывает 20 доставок, следующие страницы и фильтр «Требуют проверки». После восьми попыток или восьмой истёкшей аренды — DEAD. Ручной retry требует подтверждения, причины, совпадения версии и текущего получателя. Пауза и DEAD не удаляют историю.

Шестая миграция: 20261106091511_catalog_event_delivery.sql. Применяется после предыдущих пяти; затем полный Edge 0.14.0-edge и Web. /ready проверяет новые таблицы, CHECK и включённый fan-out trigger. Старые OutboxEvent не превращаются в исторические рассылки автоматически. Перед выпуском нужны прежние backup/restore и условия cutover из общей инструкции.

Проверены локально реальные HTTP, SQL inbox и Node worker: раздельные получатели, неподписанный 200, подпись ядра, scoped export, rollback source/fan-out, потеря ответа после remote commit, SIGKILL до complete ядра, повтор DUPLICATE и единственная строка inbox. Дополнительно проверены настройка получателя на 390 px, включение TEST, ручной DEAD retry и смена generation. Выпуск в живом ProCosmetics следует за сверкой каталога и заказов.
